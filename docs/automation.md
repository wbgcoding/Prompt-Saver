# Automation

This file is for a script, agent, or any other program driving Prompt Saver
without a human at the keyboard. It exists so a caller never has to read
Rust source, guess at a JSON shape, or ask a person what a command does.

## What this is, and what it is not

Prompt Saver has one way in for a program: the command line
(`prompt-saver <command> ...`). It runs the same command set whether a
window is open or not -- there is no separate "automation API" with its own
rules to learn.

What it is not: a general-purpose scripting language, a way to reach another
machine on the internet, or a way to skip the confirmation a destructive
command normally needs. Every command that changes something still needs
`--yes` -- nothing here is auto-confirmed just because a program is asking
instead of a person.

## Invocation

**Command line**, run on the machine Prompt Saver is installed on:

```
prompt-saver <command> [arguments] [--json] [--yes]
```

When no instance of the app is running, the launch runs the one command
itself, headless, and exits. When one is running, the launch hands its argv
to that instance over a local named pipe and prints whatever it answers.
Either way exactly one process ever touches the database at a time, and the
caller cannot tell the difference from the outside -- same exit codes, same
stdout, same stderr, whether or not a window happens to be open.

The first word decides what a launch is: nothing, `--minimized` or a file
path opens the window, anything else is a command. A mistyped command (or a
flag placed before the command) exits 1 with a message; it never opens the
window.

The program is a Windows GUI executable, so a shell may return to its prompt
before the command has finished. Wait for it and read its exit code with
`Start-Process -Wait -PassThru` (PowerShell) or `start /wait` (cmd). Output
is written to the console it was started from, or to a redirect.

Everything printed is UTF-8 without a byte order mark. A program that
captures it must decode it as UTF-8: in PowerShell 5.1 set
`[Console]::OutputEncoding = [Text.UTF8Encoding]::new($false)` first, in
Python pass `encoding="utf-8"` to `subprocess.run`. Otherwise a non-ASCII
name arrives garbled.

A launch that hands its command to the running instance waits for the result: up to 5 seconds
for the instance to take the request, then up to 10 minutes for the answer (a backup, restore or
export can run long). After that it prints a message to stderr and exits 3; the command may still
be running in the app, so check before running it again.

Add `--json` to any command that supports it for machine-readable output
instead of the plain tab-separated lines a person would read.

## Discovering the command set

`prompt-saver describe` prints the same table below as JSON -- the
authoritative, always-current list, straight from the binary itself rather
than this file. A program that wants to stay correct across an update the
person installs without rereading this page should call `describe` once at
startup instead of hard-coding a copy of the table.

```json
{
  "app": "Prompt Saver",
  "version": "3.1.0",
  "commands": [ { "name": "list", "usage": "...", "description": "...", "mutating": false }, ... ],
  "exit_codes": { "0": "ok", "1": "bad invocation", "2": "not found", "3": "store locked or unavailable", "4": "refused" }
}
```

`--json` on a plain, non-mutating command switches its stdout from
tab-separated lines to one of the shapes below (each response is the exit-0
success shape; an error never mixes JSON and plain text, see "Errors"):

```json
// list / search --json: an array of prompt summaries
[{ "id": "p_ab12cd", "name": "Release notes", "favorite": true, "tags": ["work", "release"] }]

// get --json: one prompt's full fields
{ "id": "p_ab12cd", "name": "Release notes", "text": "...", "favorite": true, "tags": ["work"], "notes": "", "color": "#4a7dff", "trashed": false }

// tag list --json
[{ "name": "work", "count": 12 }]

// view list --json
[{ "id": "v_ef34gh", "name": "Default", "members": 8 }]

// backup list --json
// "prompts" is null when the backup's count cannot be read
[{ "name": "2026-09-20_120000", "size": 40960, "prompts": 12 }]

// backup create --json
{ "name": "2026-09-25_090000" }

// add / view add --json: the new row's id
{ "id": "p_new001" }

// edit / restore --json
{ "ok": true }

// settings get --json: the raw value (string, number, bool or null)
```

## Errors

An error is always printed to stderr as plain text, never JSON, even when
`--json` was passed -- a script should read the exit code first and only
parse stdout as JSON once it is 0.

| Exit code | Meaning |
| --- | --- |
| 0 | ok |
| 1 | bad invocation (missing/unknown argument, wrong flag value), or a file that cannot be read or written (`import`, `export`) |
| 2 | not found (unknown id, unknown backup name, unknown setting key, an `import` file that does not exist) |
| 3 | store locked or unavailable (another machine holds the data folder, the database did not open, or a row failed to decrypt), or a command handed to the running instance gave no result: it was busy and did not accept the request within 5 seconds, could not be reached, or returned nothing within 10 minutes (the command may still be running) |
| 4 | refused (a mutating command run without `--yes`, a confidential prompt that can only be read, copied or changed in the app, a setting only the app may change, or a value that fails validation) |

## Limits

- `add`, `edit`, `delete`, `restore`, `tag add`, `tag remove`, `view add`,
  `view remove`, `import`, `backup restore` and `settings set` all need
  `--yes`; without it the command is refused (exit 4) and the output says
  what it would have done, so a script that forgot the flag
  still learns what it almost triggered.
- `export --ids` takes at least one id: an empty list is refused (exit 1)
  instead of exporting everything, and an id that is not in the library
  stops the export with exit 2, naming it, before anything is written.
- A path given to `export` or `import` is either absolute or relative to the
  directory the command was typed in. A drive-relative path such as
  `C:out.json` is refused (exit 1) because it would depend on the app's own
  current directory.

## Examples

Every example below uses placeholder ids/paths -- `p_demo01` is never a real
prompt id from any live database, and `C:\path\to\...` is never a path on a
real machine.

### 1. Add an entry

```
prompt-saver add --name "Release checklist" --text "1. Bump version..." --tags work,release --yes --json
```
```json
{ "id": "p_demo01" }
```

### 2. Search

```
prompt-saver search "release" --tag work --json
```
```json
[{ "id": "p_demo01", "name": "Release checklist", "favorite": false, "tags": ["work", "release"] }]
```

### 3. Fill a placeholder prompt

Prompt Saver's placeholder syntax (`docs/help.md`) is filled in the app's own
popup. The command line has no "fill" step, and `edit` would overwrite the
stored text for good, so a script reads the template, fills it itself and puts
the result where it needs it. `copy` puts the stored text on the clipboard
with its placeholders unfilled.

```
prompt-saver get p_demo01 --json
```
```json
{ "id": "p_demo01", "name": "Release checklist", "text": "Version: {?version}", "favorite": false, "tags": ["work"], "notes": "", "color": "", "trashed": false }
```

The script replaces `{?version}` in the returned `text` (for example with
`2.7.0`) and uses the result in its own way, such as `Set-Clipboard` in
PowerShell. The stored prompt stays as it was.

### 4. Take a backup

```
prompt-saver backup create --keep 10 --json
```
```json
{ "name": "2026-09-25_090000" }
```
